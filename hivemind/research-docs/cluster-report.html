Hive cluster: 8 HiveMind VMs sharing work through the kernel

One coordinator VM decides in its kernel which worker VM runs each job. Workers run real compute, report load every second, and send results back into the coordinator's shared memory graph, where they count as untrusted until checked. Everything below was measured on one laptop (13th Gen Intel(R) Core(TM) i5-13420H, 12 logical CPUs), one repetition per configuration.

Round robin decides up front and gives the slow worker a quarter of the jobs; the others finish early and wait (their CPU average drops). Least loaded and speed-aware placement watch what is in flight and shift work away from w1. Speed-aware placement was not reliably better than least loaded: it was slightly faster in an earlier run (14.5 s vs 15.3 s) and slower in this one.

3. Where it stops scaling

Tiny jobs. 96 small matrix products (a few milliseconds each) ran only 1.6x faster on 8 workers than on 1, with workers at about 20% CPU. Each job costs a round trip over the emulated serial mesh, which is slower than the job itself. Jobs need to be far larger than the messages that carry them.

12 model calls (sentiment, llama3.2:3b): 42.4 s on 1 worker, 13.1 s on 4

Model jobs gain less (3.2x on 4 workers): all workers share one Ollama on the same laptop, so the model, not the cluster, is the limit.

4. Results from a worker are not trusted until checked

A share of results is re-run on a different worker. If the two disagree, the coordinator recomputes the job itself, quarantines whoever was wrong, and re-runs everything that worker produced. In the last two runs, worker w2 was switched to corrupt one result in five.

In an earlier benchmark (record cluster_bench-20261115-102540.json, older design where the coordinator re-ran samples itself), 25% checking missed w2's one bad result and it was accepted. Checking a sample is probabilistic: with 25% checking, each corrupted result has a 1 in 4 chance of being re-run, so a bad worker can slip results through before it is caught. Checking everything is certain but runs every job twice.

5. A worker VM dies mid-run

4 seconds into a 64-job run, the harness killed one worker's VM. Its heartbeats stopped; after 3.5 s the coordinator declared it lost and re-routed the 2 job(s) it was holding.

each bar is one job on one worker; dashed red = lost with the VM

6. A pipeline across machines

Eight workers counted primes in slices (map). The coordinator summed them from its shared memory graph (reduce): 449202, which matches the host's count (449,202). A worker then asked the model to report it: "There are 449,202 primes in the range.". Total 4.8 s.

What this does and does not show

  • Each HiveMind kernel is single-core; the cluster spreads work across host cores by running one VM per core. The kernel itself does not schedule across cores.
  • The coordinator's kernel makes every placement decision. The host hub only forwards messages to the named VM and measures CPU.
  • One repetition per configuration on one laptop; timings move with whatever else the machine is doing.
  • The mesh is an emulated serial line: fine for jobs of a second, a bottleneck for jobs of milliseconds.
  • Workers run a fixed set of job kinds with bounded sizes. No code travels over the mesh.
